Восстановление Vertica ROSA_DWH_PROD из продового бэкапа

Отчёт о проделанном процессе · краткая хронология + подробная версия

SSH починен Кластер создан (3 ноды UP) Конфиг бэкапа разложен S3-креды → заменить Restore → выполнить

Краткая версия (хронология)

  1. Попробовали install_vertica — ошибка доступа SSH (ключ просил подтверждение, команда падала).
  2. То же самое с update_vertica.
  3. Починили SSH.
  4. Сделали update_vertica --add-hosts — новая нода влита в кластер.
  5. Сделали db_add_node — получилось 4 ноды. Но старую удалить не получится: она в статусе DOWN.
  6. Решили пока оставить дев-базу и рядом создать прод: stop_db, затем create_db.
  7. База создалась. Три ноды UP.
  8. Ушли спать.
  9. Нужно подготовить файлы конфига загрузки бэкапа, как на проде (остался в репе vertica-backup-config/production).
  10. Подготовили конфиг, вставили на все ноды через cat > /home/dbadmin/backup_s3_11_prod.ini << 'EOF'.
  11. Нужно заменить S3-пользователя, через которого читается бэкап (права только на чтение, чтобы не испортить данные в S3).
  12. Подменяем в /home/dbadmin/.aws/credentials.
  13. Можно переходить к запуску восстановления.
  14. Как сделать, чтобы терминал не отключился при долгой работе restore.
  15. Остановить Vertica: admintools -t stop_db -d ROSA_DWH_PROD -p <DB_PASSWORD>.
  16. Запустить восстановление: export …; vbr -t restore -c /home/dbadmin/backup_s3_11_prod.ini.

Подробная версия

1–2. Ошибки SSH при install_vertica / update_vertica

Vertica при установке/добавлении хостов ходит по SSH под пользователем dbadmin на все ноды кластера. Симптомы — «Permission denied (publickey)» и запрос подтверждения host-ключа.

Причина У dbadmin не был настроен passwordless SSH на удалённые ноды. Из доки: «The administrative account must be able to SSH to all hosts without specifying a password». Плюс host-ключи не были приняты (первое подключение).

Отдельно путало то, что install_vertica -s localhost (из гайда коллеги) — вообще тупиковый путь: узел с localhost потом нельзя влить в кластер.

3. Починили SSH

Настроили passwordless SSH для dbadmin на все ноды и приняли host-ключи.

# под dbadmin на инициаторе
ssh-keygen -t rsa -b 4096 -N "" -f ~/.ssh/id_rsa
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat ~/.ssh/id_rsa.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
ssh-copy-id dbadmin@<нода2>
ssh-copy-id dbadmin@<нода3>
ssh-copy-id dbadmin@<клон>

Проверка: ssh dbadmin@<нода> hostname — без пароля, возвращает имя нужной ноды.

4–5. update_vertica --add-hosts и db_add_node → 4 ноды

Новый хост влили в кластер, затем добавили ноду в БД. Стало 4 ноды, но старая (мёртвая node0002) осталась в статусе DOWN.

DOWN-ноду удалить нельзя Vertica не даёт удалить ноду, пока хоть одна нода DOWN: ошибка «All nodes must be UP or STANDBY before dropping a node» — даже если удаляешь именно упавшую. Чистого способа «выкинуть» её без замены/пересоздания нет.

6–7. Оставили dev и создали prod рядом

Пошли обходным путём: stop_db ROSA_DWH_DEV → create_db ROSA_DWH_PROD. Дев-база просто остановлена и остаётся «зависшей» (её node0002 мертва).

admintools -t stop_db -d ROSA_DWH_DEV -p '<пароль>' -F
admintools -t create_db \
  --database=ROSA_DWH_PROD \
  --password='<пароль>' \
  --hosts=10.244.20.50,10.244.20.150,10.244.20.201 \
  --catalog_path=/media/data/vertica --data_path=/media/data/vertica
Итог шага БД ROSA_DWH_PROD создана, ноды автоматически назвались v_rosa_dwh_prod_node0001/2/3, все три UP.

Формально «переименование» dev → prod в Vertica невозможно (нет ALTER DATABASE … RENAME); единственный путь — пересоздать БД с нужным именем. Что и было сделано.

9–10. Конфиг бэкапа разложен на ноды

Продовый конфиг backup_s3_11_prod.ini забрали из репозитория и создали на всех нодах через heredoc. Ключевое — последняя строка EOF без кавычек.

cat > /home/dbadmin/backup_s3_11_prod.ini << 'EOF'
[S3]
s3_backup_path = s3://analytics-prod-vertica-backup/prod-11/
s3_backup_file_system_path = []:/home/dbadmin/backup_locks_dir_11/

[Misc]
retryCount = 15
retryDelay = 10
tempDir = /media/data/vertica_backup_11
restorePointLimit = 2

[Database]
dbName = ROSA_DWH_PROD
dbPromptForPassword = True

[Transmission]
concurrency_backup = 4
port_rsync = 50000
EOF
chmod 600 /home/dbadmin/backup_s3_11_prod.ini
Нюансы конфига
  • Секция [S3] — устаревшая (deprecated с 10.1), но в 11.0 работает. [CloudStorage] — её замена, но их нельзя совмещать; и переводить бэкап на неё не нужно.
  • [Mapping] не добавлять — взаимоисключим с [S3].
  • snapshotName не задаём (в проде был закомментирован) — фактическое имя серии покажет quick-check.
  • Создать каталоги из конфига: mkdir -p /media/data/vertica_backup_11 /home/dbadmin/backup_locks_dir_11.

11–12. Замена S3-пользователя (только чтение)

Подменяем креды в /home/dbadmin/.aws/credentials, по возможности на нодах все — данные при restore тянут все ноды, хотя дока и говорит про «initiator host».

# бэкап текущих
cp -a /home/dbadmin/.aws /home/dbadmin/.aws.bak.$(date +%Y%m%d_%H%M%S)

# новые креды (read-only пользователь)
cat > /home/dbadmin/.aws/credentials << 'EOF'
[default]
aws_access_key_id = <НОВЫЙ_KEY_ID>
aws_secret_access_key = <НОВЫЙ_SECRET>
EOF
chown -R dbadmin:verticadba /home/dbadmin/.aws
chmod 700 /home/dbadmin/.aws
chmod 600 /home/dbadmin/.aws/credentials

# раздать на остальные ноды
for h in 10.244.20.150 10.244.20.201; do
  sudo -u dbadmin scp -r /home/dbadmin/.aws dbadmin@$h:/home/dbadmin/
done
Проверьте env-переменные Если в сессии заданы AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY, они перебьют файл. Уберите: unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY.

14. Чтобы терминал не отключился при долгом restore

Не держать процесс в foreground SSH-сессии — иначе при обрыве он получит SIGHUP и умрёт. Использовать tmux/screen (лучше) или nohup.

# tmux — рекомендую
sudo apt install -y tmux
tmux new -s restore
# … запускаем restore внутри …
# отсоединиться: Ctrl+B, затем D
# вернуться:    tmux attach -t restore

# либо nohup, без доп. пакетов
nohup vbr -t restore -c /home/dbadmin/backup_s3_11_prod.ini > /home/dbadmin/restore.log 2>&1 &

MobaXterm: включите keepalive (Settings → SSH → keepalive, 30–60 с) — это снижает риск разрыва по простою, но не спасает от внезапного обрыва, поэтому tmux/nohup всё равно нужны.

15. Остановка БД (обязательна для полного restore)

# закрыть сессии
/opt/vertica/bin/vsql -U dbadmin -w '<DB_PASSWORD>' -c "SELECT CLOSE_ALL_SESSIONS();"

# остановить базу
/opt/vertica/bin/admintools -t stop_db -d ROSA_DWH_PROD -p '<DB_PASSWORD>'
Важно Полный restore выполняется только на остановленной БД. Точечный (--restore-objects) — можно на работающей, но у нас полный.

16. Запуск полного восстановления

export VBR_BACKUP_STORAGE_ENDPOINT_URL=https://storage.yandexcloud.net/
export VBR_COMMUNAL_STORAGE_ENDPOINT_URL=https://storage.yandexcloud.net/

# холостая проверка (можно и до stop_db)
vbr -t quick-check -c /home/dbadmin/backup_s3_11_prod.ini

# ПОЛНЫЙ restore — БЕЗ --restore-objects
vbr -t restore -c /home/dbadmin/backup_s3_11_prod.ini
  • Без --restore-objects — иначе восстановится только один объект.
  • Конкретный архив: --archive='YYYYMMDD_HHMMSS' (доступно ~3 дня).
  • Полный restore восстанавливает всё: схемы, таблицы, проекции, а также пользователей/роли/привилегии.

После завершения — старт и проверка

/opt/vertica/bin/admintools -t start_db -d ROSA_DWH_PROD -p '<DB_PASSWORD>'

/opt/vertica/bin/vsql -U dbadmin -w '<DB_PASSWORD>' -c \
  "SELECT node_name, node_state FROM node_states ORDER BY 1;"
/opt/vertica/bin/vsql -U dbadmin -w '<DB_PASSWORD>' -c \
  "SELECT COUNT(*) FROM <таблица>;"

Как контролировать процесс

# прогресс самого vbr ("Copying... N out of M, X%")
tail -f /home/dbadmin/restore.log

# логи vbr в tempDir
ls -lt /media/data/vertica_backup_11/ | head
tail -f /media/data/vertica_backup_11/<свежий>.log

# процесс жив?
ps aux | grep -i vbr | grep -v grep

# в tmux/screen — просто переподключиться
tmux attach -t restore
