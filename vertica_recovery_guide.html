Восстановление кластера Vertica ROSA_DWH

Превращение дев-кластера в полную копию погибшего прода + накат бэкапа

Версия Vertica: 11.0.1.0  ·  Платформа: Debian / Ubuntu (.deb)  ·  Режим spread: point-to-point

1. Ситуация

  • Прод-кластер Vertica (3 ноды) полностью потерян. Есть полный бэкап данных.
  • В дев-кластере уцелело 2 ноды. Третья нода (node0002) потеряна и числится в каталоге как DOWN.
  • DevOps подняли ресурсы живых нод до продовых и развернули третью ноду как клон node0001.
  • Цель: сделать дев полностью идентичным старому проду (имя БД и имена нод как на проде) и накатить бэкап.

2. Зафиксированные факты

Версия Vertica11.0.1.0 (vertica_11.0.1-0_amd64.deb)
Режим spreadpoint-to-point (unicast, явные IP нод)
Продовая БДROSA_DWH_PROD → ноды v_rosa_dwh_prod_node0001/2/3

node000210.244.20.100 — потеряна, DOWN (в каталоге)

Ключевой механизм Имя ноды Vertica = v_<имя_БД>_node000N (производное от имени БД). Поэтому достаточно создать БД с продовым именем ROSA_DWH_PROD — ноды автоматически станут v_rosa_dwh_prod_node000X, и маппинг при restore не понадобится.
Критично: DOWN-ноду удалить нельзя Vertica запрещает удалять ноду, пока хоть одна нода в состоянии DOWN (ошибка «All nodes must be UP or STANDBY before dropping a node» — даже если удаляем именно упавшую ноду). Единственный чистый способ избавиться от записи о node0002 — дропнуть всю БД (дроп БД автоматически убирает определения нод).
Критично: не перепутать машины Клон — это точная копия живой node0001. Если случайно выполнить удаление каталога/данных на оригинальной node0001 — потеряете живую ноду. Все команды с пометкой КЛОН выполняются только на клоне.

3. Фаза 0 — Дедупликация ОС на клоне КЛОН

Клон виртуальной машины несёт идентичность node0001 (hostname, SSH-ключи, machine-id). Перед выходом в сеть её нужно сделать уникальной. IP уже сменён DevOps.

0.1 Проверка, что мы на клоне, а не на node0001

hostname          # должно быть ИМЯ КЛОНА, не node0001
hostname -I       # должен быть НОВЫЙ IP клона, не 10.244.20.50
Стоп-проверка Если hostname/IP не те — НЕ продолжать. Вы не на той машине.

0.2 Уникальный hostname

sudo hostnamectl set-hostname <новое_уникальное_имя>

0.3 Файл /etc/hosts

sudo vi /etc/hosts
# заменить старые записи hostname/IP node0001 на новые
# проверить, что имя резолвится в IP КЛОНА:
getent hosts $(hostname)

0.4 Перегенерация SSH host-ключей

# иначе клон и node0001 имеют одинаковые SSH host-ключи —
# это ломает SSH внутри кластера и даёт MITM-предупреждения
sudo rm -f /etc/ssh/ssh_host_*
sudo ssh-keygen -A
sudo systemctl restart ssh

0.5 Перегенерация machine-id

sudo rm -f /etc/machine-id
sudo systemd-machine-id-setup

4. Фаза 1 — Vertica-уровень на клоне КЛОН

Клон содержит каталог и данные node0001, а также admintools.conf и spread.conf с идентичностью node0001 и старым IP 10.244.20.50. Всё это нужно убрать, чтобы клон не «прикинулся» node0001.

1.1 Проверить, не запущена ли Vertica

ps aux | grep -i vertica | grep -v grep
systemctl list-unit-files | grep -i vertica

1.2 Остановить и отключить автозапуск

sudo systemctl stop vertica_agent 2>/dev/null
sudo systemctl disable vertica_agent 2>/dev/null

# если найден запущенный процесс БД — остановить:
/opt/vertica/sbin/admintools -t stop_db -d ROSA_DWH_DEV 2>/dev/null

1.3 Удалить клонированные каталог и данные node0001

Сначала посмотреть, что лежит:

ls -la /media/data/vertica/
ls -la /media/data/vertica/ROSA_DWH_DEV/

Убедиться, что это ...node0001_catalog / ...node0001_data, и удалить:

sudo rm -rf /media/data/vertica/ROSA_DWH_DEV/v_rosa_dwh_dev_node0001_catalog
sudo rm -rf /media/data/vertica/ROSA_DWH_DEV/v_rosa_dwh_dev_node0001_data
Почему это безопасно Данные дева всё равно будут затёрты полным restore, а БД ROSA_DWH_DEV будет удалена. Главное — клон не должен поднять Vertica с идентичностью node0001.

5. Фаза 2 — Добавить ноду в кластер ЖИВАЯ НОДА

Выполняется с одной из живых нод (node0001 или node0003). Скрипт сам ставит пакет на клон, проверяет связность, переконфигурирует spread и admintools.

/opt/vertica/sbin/update_vertica \
  --add-hosts <НОВЫЙ_IP_КЛОНА> \
  --deb /media/data/distrib/vertica_11.0.1-0_amd64.deb \
  --dba-user dbadmin \
  --dba-user-password '<ОС-пароль_dbadmin>' \
  --point-to-point
Обязательно --point-to-point Кластер работает в режиме point-to-point. Если не указать флаг — spread переключится на broadcast, и кластер сломается («cluster communication problems that prevent Vertica from running properly»).
Что такое --dba-user-password Это ОС-пароль системного пользователя dbadmin (тот, которым заходите по ssh), а НЕ пароль базы Vertica. Он должен быть одинаковым на всех нодах кластера. 
# проверка — хост появился в кластере
admintools -t list_allnodes

6. Фаза 3 — Пересоздать БД под прод ЖИВАЯ НОДА

Удаляем дев-БД (вместе с записью о DOWN-node0002) и создаём свежую БД с продовым именем.

3.1 Остановить и дропнуть dev-БД

admintools -t stop_db -d ROSA_DWH_DEV -p '<DB_PASSWORD>'
# если упрётся из-за лежащей node0002 — форсировать:
# admintools -t stop_db -d ROSA_DWH_DEV -p '<DB_PASSWORD>' -F

admintools -t drop_db -d ROSA_DWH_DEV

3.2 Создать БД с продовым именем на 3 нодах

admintools -t create_db \
  --database=ROSA_DWH_PROD \
  --password='<DB_PASSWORD>' \
  --hosts=10.244.20.50,10.244.20.150,<НОВЫЙ_IP_КЛОНА> \
  --catalog_path=/media/data/vertica \
  --data_path=/media/data/vertica
Внимание к списку --hosts Туда идут три живых адреса: node0001 (10.244.20.50), node0003 (10.244.20.150) и клон (<НОВЫЙ_IP_КЛОНА>). Мёртвый 10.244.20.100 включать нельзя. Ноды v_rosa_dwh_prod_node0001/2/3 создадутся автоматически.
Пути каталога/данных Для restore пути каталога должны совпадать с продовыми. Подтвердите базу (/media/data/vertica) по cat /opt/vertica/config/admintools.conf.

7. Фаза 4 — Restore из бэкапа ЖИВАЯ НОДА

4.1 Подготовить vbr-конфиг

# скопировать продовой vbr.ini на ноду
scp <откуда_есть_бэкап>:<путь_vbr.ini> /home/dbadmin/vbr.ini

# проверить ключевые секции
cat /home/dbadmin/vbr.ini

Обязательно должно быть:

  • [database] → dbName = ROSA_DWH_PROD
  • [Mapping] → v_rosa_dwh_prod_node000X = <backupHost>:<backupDir>
  • бэкап-директория доступна с нод дев-кластера

4.2 Остановить БД (restore требует DOWN)

admintools -t stop_db -d ROSA_DWH_PROD -p '<DB_PASSWORD>'

4.3 Запустить restore

vbr --task restore --config-file /home/dbadmin/vbr.ini
Требования полного restore (из доки) Целевая БД должна: быть DOWN; иметь то же имя, то же число нод и идентичные имена нод, тот же путь каталога и те же порты, что и источник. Все эти условия выполняются: БД ROSA_DWH_PROD, 3 ноды v_rosa_dwh_prod_node000X.

8. Фаза 5 — Проверка ЖИВАЯ НОДА

# старт БД после restore
admintools -t start_db -d ROSA_DWH_PROD -p '<DB_PASSWORD>'

# все ноды UP
vsql -U dbadmin -w '<DB_PASSWORD>' -c \
  "SELECT node_name, node_state FROM node_states ORDER BY 1;"

# контрольная проверка данных
vsql -U dbadmin -w '<DB_PASSWORD>' -c \
  "SELECT COUNT(*) FROM <проверочная_таблица>;"

Приложение A — Как определить режим spread

Актуальный конфиг spread хранится в каталоге БД (не в /opt/vertica/config). Путь виден в аргументе -c запущенного процесса:

ps -ef | grep -i spread | grep -v grep
# пример:
# .../spread -c /media/data/vertica/<DB>/v_<db>_node000N_catalog/spread.conf -D ...

Открыть найденный файл и посмотреть блок Spread_Segment:

РежимКак выглядит конфиг
point-to-point Явные IP каждой ноды с метками N<ip>: 
Spread_Segment 10.244.20.50:4803 {
  N010244020050  10.244.20.50 { 10.244.20.50 }
}
broadcast Один сегмент с broadcast-адресом подсети: 
Spread_Segment 4803 {
  10.244.20.255
}

Приложение B — Пароли: что куда

ПарольЧто этоГде используется
ОС-пароль dbadmin Пароль системного (Linux) пользователя dbadmin ssh dbadmin@..., sudo, --dba-user-password
Пароль БД Пароль Vertica-суперпользователя dbadmin vsql -w, create_db --password, stop_db -p, vbr
Как отличить ОС-пароль — то, чем заходите по ssh. Пароль БД — то, чем заходите в vsql. В командах update_vertica используется ОС-пароль.

Приложение C — Чек-лист

  • Новый IP у клона (сделан DevOps)
  • Уникальный hostname клона
  • Поправлен /etc/hosts
  • Перегенерированы SSH host-ключи
  • Перегенерирован machine-id
  • Vertica на клоне остановлена и не стартует сама
  • Удалён клонированный каталог/данные node0001 (на клоне!)
  • Клон добавлен в кластер (update_vertica --add-hosts --point-to-point)
  • Dev-БД ROSA_DWH_DEV остановлена и удалена
  • Создана БД ROSA_DWH_PROD на 3 нодах (3 ноды UP, K=1)
  • Подготовлен и проверен vbr.ini (dbName = ROSA_DWH_PROD)
  • БД остановлена, выполнен vbr --task restore
  • БД запущена, ноды UP, данные проверены
